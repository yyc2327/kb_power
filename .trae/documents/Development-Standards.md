# 企业级知识库管理系统 - 开发规范

## 1. 代码风格规范

### 1.1 TypeScript 编码规范

本项目使用 TypeScript 作为主要的开发语言，充分利用 TypeScript 的类型系统可以显著提升代码质量和开发效率。所有代码文件应使用 .ts 或 .tsx 扩展名，React 组件使用 .tsx 扩展名，普通工具函数和类型定义使用 .ts 扩展名。应避免使用 any 类型，尽可能使用精确的类型定义。如果确实无法确定类型，可以使用 unknown 代替 any，并在使用时进行类型断言或类型守卫。所有接口和类型应使用 PascalCase 命名法，例如 UserInfo、KnowledgeGraph、GraphNode。类型定义应尽量完整和精确，包括函数参数、返回值、泛型约束等。禁止使用 @ts-ignore 或 @ts-nocheck 等指令，除非在特殊情况下并添加详细的注释说明原因。

变量和函数命名应遵循 camelCase 命名法，变量名应使用名词或名词短语，函数名应使用动词或动词短语。布尔类型的变量应使用 is、has、should、can 等前缀，例如 isLoading、hasPermission、shouldUpdate。常量应使用全大写字母和下划线命名，例如 MAX_RETRY_COUNT、DEFAULT_PAGE_SIZE。枚举类型应使用 PascalCase 命名，枚举值应使用全大写字母和下划线命名，例如 enum Status { DRAFT_PENDING, APPROVED, PUBLISHED }。

### 1.2 React 组件规范

React 组件应遵循函数式组件和 Hooks 的开发模式，不再使用类组件。组件文件应使用 PascalCase 命名法，例如 KnowledgeCard.tsx、GraphCanvas.tsx。组件应保持单一职责原则，每个组件只负责一个功能或关注点。组件的代码应按以下顺序组织：导入语句、类型定义、组件定义、样式定义（如果使用 CSS-in-JS）。组件内部应避免定义过长的函数，如果逻辑复杂，应将业务逻辑抽取到自定义 Hooks 中。组件的 Props 接口应使用 ComponentNameProps 命名，例如 interface KnowledgeCardProps。

组件的 Props 类型定义应明确每个属性的类型和是否必填，避免使用可选属性过多的情况。对于可选的 Props，应提供合理的默认值。组件的默认Props 应使用函数参数的默认值或 defaultProps（已废弃），而不是在组件内部进行判断处理。组件不应直接修改传入的 Props，如果需要响应变化，应使用受控组件模式或状态提升。组件的内部状态应最小化，优先使用 Props 或全局状态。

### 1.3 代码格式规范

本项目使用 Prettier 作为代码格式化工具，所有代码应通过 Prettier 自动格式化后再提交。缩进应使用两个空格，避免使用 Tab 字符。行宽度建议不超过 120 个字符，超长行应适当换行。换行应遵循统一的风格，在运算符后换行而非前导，保持代码的可读性。空行应合理使用，函数之间使用一个空行，导入语句之间使用空行分组。分号应始终使用，即使 JavaScript 的自动分号插入机制可以工作。引号应使用单引号包裹字符串，双引号仅在字符串包含单引号或用于 JSX 属性时使用。

花括号的使用应保持一致，左花括号应与控制语句放在同一行，例如 if (condition) {。条件语句即使只有一行，也应使用花括号包裹。函数定义、类定义、控制语句等应使用 K&R 风格的花括号放置。空格应合理使用，运算符前后、逗号后面、冒号后面（对象字面量）应添加空格。函数参数、数组元素、对象属性之间应保持一致的空格格式。

### 1.4 CSS 和样式规范

本项目使用 Tailwind CSS 作为主要的样式解决方案，应充分利用 Tailwind 提供的工具类进行样式开发。组件的样式应优先使用 Tailwind 工具类，只有在工具类无法满足需求时才使用自定义 CSS。Tailwind 的配置应保持简洁，避免过度自定义。复杂的样式逻辑应抽取为 Tailwind 插件或自定义工具类。响应式设计应使用 Tailwind 的前缀（sm、md、lg、xl、2xl），移动优先设计，先编写移动端样式，再添加大屏幕的样式覆盖。

对于需要动态计算的样式或复杂的组件状态样式，应使用 CSS-in-JS 方案（如 styled-components 或 Emotion）。组件的样式应与组件文件放在一起，便于维护和查找。样式类名应使用语义化命名，避免使用描述外观的类名（red、big 等）。全局样式和 CSS 变量应在统一的入口文件中定义，保持样式的一致性和可维护性。

## 2. 命名规范

### 2.1 文件命名规范

文件的命名应清晰表达文件内容，并遵循统一的命名约定。TypeScript 和 JavaScript 源文件应使用 camelCase 命名法，例如 useKnowledgeSearch.ts、knowledgeStore.ts。React 组件文件应使用 PascalCase 命名法，与组件名称保持一致，例如 KnowledgeTree.tsx、ReviewQueue.tsx。测试文件应与被测试文件同名，后缀为 .test.ts(x) 或 .spec.ts(x)，例如 knowledgeApi.test.ts、KnowledgeCard.spec.tsx。样式文件应与对应的组件文件同名，后缀为 .module.css 或使用 Tailwind 工具类替代。配置文件应使用小写字母和连字符，例如 tsconfig.json、.env.example、vite.config.ts。

资源文件（图片、字体、图标）应使用描述性名称，包含类型前缀或后缀，例如 icon-logo.svg、bg-dashboard.png、font-heading.woff2。文件夹命名应使用 kebab-case 命名法，与文件名保持一致，例如 components/layout、pages/Dashboard、hooks/useKnowledge。

### 2.2 目录结构规范

项目的目录结构应遵循清晰的分层原则，便于代码的查找和维护。src 目录作为主要的源代码目录，包含所有业务代码。components 目录存放通用组件，按照功能分为 layout（布局组件）、knowledge（知识组件）、graph（图谱组件）、collaboration（协作组件）等子目录。pages 目录存放页面级组件，按照路由路径组织，每个页面一个独立文件夹。stores 目录存放 Zustand 状态管理相关的文件，每个 store 独立一个文件。hooks 目录存放自定义 Hooks，按照功能或使用场景组织。types 目录存放 TypeScript 类型定义文件，类型定义应按模块划分。utils 目录存放工具函数，按照功能分组。mock 目录存放模拟数据，用于开发和测试。

每个目录应包含 index.ts 文件作为入口文件，统一导出目录内的主要模块。目录结构应保持扁平化，避免过深的嵌套层次。如果某个目录下的文件数量超过 20 个，应考虑进一步拆分或重组。

### 2.3 变量命名规范

变量命名应清晰表达变量的用途和含义，避免使用模糊或过于简短的名称。临时变量可以使用简短名称，如循环变量 i、j、k，但应避免在嵌套循环中使用单字母变量名。DOM 引用应使用 ref 作为后缀，如 buttonRef、inputRef。事件处理函数应使用 handle 作为前缀，handleClick、handleSubmit、handleChange。获取数据的函数应使用 fetch、get、load 作为前缀，如 fetchKnowledge、getUserInfo、loadGraphData。异步操作函数应使用 async 关键字，返回 Promise 对象。状态变量应使用 set 作为前缀的函数进行更新，如 setLoading、setKnowledgeList。

布尔变量应使用形容词或动词的过去分词，如 isEmpty、isLoading、hasError、isVisible。数组变量应使用复数名词或数组后缀，如 users、knowledgeList、graphNodes。对象变量应使用单数名词或驼峰命名，如 userInfo、graphData。函数返回值应使用 result、data、response 等名称，如 fetchUserResult。

### 2.4 接口与类型命名规范

接口和类型是 TypeScript 最重要的特性之一，应精心设计接口和类型的命名。接口名称应使用 PascalCase 命名法，名称应清晰表达实体的含义。用户相关的接口应使用 User、UserInfo、UserProfile 等名称。知识相关的接口应使用 Knowledge、KnowledgeItem、KnowledgeGraph 等名称。图谱相关的接口应使用 GraphNode、GraphEdge、GraphData 等名称。分页相关的接口应使用 Page、PageResult、Pagination 等名称。

接口的命名应避免使用 I 前缀或 Model 后缀等旧的命名约定。类型别名应使用 type 关键字声明，而非 interface（除非需要声明合并或扩展）。联合类型和交叉类型应使用语义化的括号和空格。泛型参数应使用有意义的名称，如 T、U 等单字母仅在上下文清晰时使用。复杂类型应添加注释说明其结构和用途。

## 3. 组件规范

### 3.1 组件设计原则

组件是 React 应用的基本构建单元，良好的组件设计是构建可维护应用的基础。组件应遵循单一职责原则，每个组件只负责一个功能或关注点。如果组件承担了过多的职责，应考虑拆分为更小的子组件。组件应保持适度的粒度，过细的粒度会导致组件数量膨胀，过粗的粒度会降低复用性。组件应具有清晰的 API，通过 Props 定义组件与外界的交互接口。组件内部应封装实现细节，对外暴露简洁一致的接口。

组件应优先使用组合模式而非继承模式，通过 Props 传递子组件实现 UI 组合。组件应避免直接访问全局状态或全局变量，应通过 Props 或 Context 接收所需数据。组件的样式应与组件逻辑分离，便于样式的复用和调整。组件应支持受控和非受控两种使用模式，通过 Props 区分控制权归属。

### 3.2 组件目录结构

每个组件应有独立的文件夹，文件夹名称与组件名称一致。组件文件夹内应包含组件实现文件（index.tsx）、类型定义文件（types.ts，如果组件有独特的 Props 类型）、样式文件（styles.module.css 或使用 Tailwind）、测试文件（index.test.tsx）、文档文件（README.md，如果组件有复杂的使用说明）。如果组件有多个子组件，子组件应放在 components 子目录下。

组件的 index.tsx 文件应作为组件的唯一导出入口。组件相关的类型定义应放在组件内部或独立的 types.ts 文件中。组件的样式应使用 CSS Modules 或 Tailwind，避免样式冲突。组件的测试应覆盖组件的主要功能和边界情况。

### 3.3 组件 Props 设计

组件的 Props 应精心设计，确保接口的易用性和稳定性。Props 的定义应使用 interface 而非 type，便于扩展和声明合并。每个 Prop 都应有明确的类型和是否必填的说明。必填的 Prop 不应使用默认值，使用者必须显式传递值。可选的 Prop 应提供合理的默认值，并使用可选操作符（?）标记。Prop 的命名应清晰表达其用途，避免过于简短或模糊的名称。

Props 的传递应避免传递过多参数，如果参数超过 5 个，应考虑使用对象参数或拆分组件。Props 的回调函数应明确参数类型和返回值类型。Props 的类型应避免使用 any，尽可能使用联合类型或泛型约束。对于复杂的 Props 类型，应添加注释说明其结构和约束条件。

### 3.4 组件状态管理

组件状态应最小化，优先考虑从 Props 接收数据或从全局状态获取。只在必要时才使用 useState 创建本地状态。本地状态应与组件紧密相关，不应在组件间共享。如果多个组件需要共享状态，应将状态提升到最近的公共祖先组件或使用 Context。状态更新应使用函数式更新形式，避免依赖当前状态值时出现闭包问题。

useState 的初始值如果是计算得到的复杂值，应使用函数形式惰性初始化。对于频繁更新的状态（如表单输入），应考虑使用 useReducer 或自定义 Hook 封装逻辑。useEffect 的依赖数组应包含所有使用的外部值，避免遗漏导致的闭包陷阱问题。应避免在 useEffect 中直接修改状态，应通过 setState 函数更新。

## 4. API 设计规范

### 4.1 RESTful API 设计原则

后端 API 应遵循 RESTful 设计原则，提供清晰、一致的接口风格。资源命名应使用名词复数形式，如 /knowledge、/domains、/graphs，避免使用动词作为资源名称。HTTP 方法应正确使用，GET 用于获取资源列表或单个资源，POST 用于创建新资源，PUT 用于更新完整资源，PATCH 用于部分更新资源，DELETE 用于删除资源。API 路径应使用 kebab-case 命名法，如 /knowledge-bases、/graph-nodes。

API 版本应通过 URL 路径前缀管理，如 /api/v1/knowledge。对于有父子关系的资源，可以使用嵌套路径表示，如 /domains/{domainId}/applications。查询参数应用于分页、排序、过滤等场景，参数名应使用 camelCase 命名。分页参数应统一使用 page 和 pageSize，默认值分别为 1 和 20。排序参数应使用 sortBy 和 sortOrder，sortOrder 可选值为 asc 和 desc。

### 4.2 请求与响应格式

请求体应使用 JSON 格式，Content-Type 应设置为 application/json。请求参数应进行必要的校验和清理，后端应返回明确的错误信息。响应体应统一使用 JSON 格式，包含状态码、消息和数据字段。成功响应的结构应为 { code: 200, message: 'success', data: {...} }。错误响应的结构应为 { code: 400, message: 'error description', data: null }。分页响应的结构应为 { code: 200, message: 'success', data: { list: [...], total: 100, page: 1, pageSize: 20 }。

日期时间应使用 ISO 8601 格式，如 2024-01-15T10:30:00Z。ID 字段应使用 UUID 格式，保证全局唯一性。金额和百分比等数值字段应使用 Number 类型，保留两位小数。布尔值应使用 true 和 false，不使用字符串 'true' 或 'false'。

### 4.3 错误处理规范

API 应返回正确的 HTTP 状态码，表明请求的处理结果。200 表示成功，201 表示创建成功，400 表示请求参数错误，401 表示未认证，403 表示无权限，404 表示资源不存在，500 表示服务器内部错误。错误响应应包含清晰的错误信息，帮助客户端理解和处理错误。错误信息应使用用户友好的语言描述，避免暴露内部实现细节。

对于验证错误，应返回详细的字段级错误信息，如 { code: 400, message: 'Validation failed', errors: [{ field: 'name', message: 'Name is required' }] }。对于业务逻辑错误，应返回业务错误码和友好的错误描述。对于系统错误，应记录详细日志，对外返回友好的错误提示。错误信息的国际化应根据客户端的 Accept-Language 头返回对应语言的错误描述。

## 5. 数据库设计规范

### 5.1 表命名与字段规范

数据库表名应使用小写字母和下划线命名法，如 knowledge_base、graph_node、user_role。表名应使用名词复数形式，表示实体集合。字段名应使用小写字母和下划线命名法，如 knowledge_title、created_at、updated_by。主键字段应命名为 id，使用 UUID 或自增整数类型。外键字段应命名为 referenced_table_name_id，如 domain_id、user_id。创建时间字段应命名为 created_at，使用 DATETIME 类型。更新时间字段应命名为 updated_at，使用 DATETIME 类型。软删除字段应命名为 deleted_at，使用 DATETIME 类型，允许为 NULL 表示未删除。

### 5.2 索引与约束规范

每个表必须有主键，禁止使用业务相关的字段组合作为主键。常用查询字段应创建索引，避免全表扫描。复合索引应将区分度高的字段放在前面。唯一约束用于保证数据的唯一性，应在需要唯一性保证的字段上创建。外键约束用于维护表间的引用完整性，应谨慎使用，避免级联删除导致的意外数据丢失。应避免创建过多的索引，每个索引都会影响写入性能。

### 5.3 数据库变更规范

数据库结构变更应使用迁移脚本管理，不应直接修改生产数据库。迁移脚本应同时包含升级和降级逻辑，确保可回滚。迁移脚本应经过测试验证后再在生产环境执行。删除字段前应确认没有代码依赖，删除前应先标记为废弃。索引创建应选择业务低峰期执行，避免长时间锁表。敏感数据字段应加密存储，使用独立的加密密钥管理。

## 6. 文档规范

### 6.1 代码注释规范

代码注释应解释为什么这样做，而非做什么，代码本身应尽可能自解释。注释应保持简洁明了，避免冗长和重复。对于复杂的业务逻辑、算法实现或设计决策，应添加注释说明背景和考虑因素。注释应与代码保持同步，过时的注释比没有注释更有害。应删除无用的注释和临时调试代码，保持代码整洁。

TODO 注释应使用统一的格式，包含作者信息和任务描述，如 // TODO(author): 实现 XX 功能。应定期清理已完成的 TODO 注释。 FIXME 注释用于标记已知的问题或需要修复的代码，如 // FIXME(author): 此处在 XX 场景下有 bug，需要修复。应使用 FIXME 标记的问题尽快修复或创建对应的任务跟踪。

### 6.2 接口文档规范

所有 API 接口都应提供文档说明，包括接口的功能、请求参数、响应格式和示例。接口文档应与代码保持同步，文档滞后会导致使用者困惑。文档工具可使用 Swagger/OpenAPI 或 Apifox，自动生成文档页面。文档应包含请求示例和响应示例，帮助使用者理解接口用法。文档应说明接口的错误码和错误信息，便于错误处理。文档应标注接口的安全认证方式和权限要求。

### 6.3 README 文档规范

每个项目都应有 README.md 文件，包含项目简介、功能特性、快速开始、部署说明、配置说明和贡献指南等章节。README 应简洁明了，突出项目的核心价值和使用方式。快速开始章节应包含环境要求、安装步骤和运行命令，使新成员能在 5 分钟内运行项目。README 应包含 Badges，展示构建状态、测试覆盖率等信息。README 应链接到详细的文档，如用户手册、开发者文档等。

### 6.4 组件文档规范

复杂的通用组件应提供组件文档，说明组件的功能、Props 接口、使用示例和注意事项。组件文档可使用 Storybook 或 JSDoc 方式展示。Props 接口应详细说明每个属性的用途、类型、默认值和必填性。使用示例应包含常见的用法场景，覆盖主要的 Props 组合。注意事项应说明组件的限制、兼容性和已知问题。组件文档应与组件代码放在一起，便于查阅和维护。

## 7. 测试规范

### 7.1 单元测试规范

核心业务逻辑应有对应的单元测试覆盖，确保逻辑的正确性。测试应遵循 Arrange-Act-Assert 模式，先准备测试数据，执行被测操作，验证预期结果。测试用例应覆盖正常流程、边界条件和异常情况。测试应具有独立性，每个测试用例应能独立运行，不依赖其他测试的执行结果。测试应具有确定性，相同的测试应始终得到相同的结果，不受外部环境影响。

测试文件应与源代码文件放在同一目录下，使用 .test.ts(x) 或 .spec.ts(x) 后缀。测试描述应清晰表达测试的场景和预期结果，如 describe('KnowledgeCard') { it('should display knowledge title correctly') }。测试应避免过度 mocking，尽可能使用真实的数据和依赖。测试应覆盖组件的 Props 变化、状态更新和生命周期方法。

### 7.2 集成测试规范

模块间的交互应有集成测试验证，确保模块间的协作正确。集成测试应使用接近真实环境的测试数据和环境。集成测试的粒度应适中，既能验证模块间协作，又不会过度复杂。集成测试的运行时间应控制合理，避免测试套件运行过慢。应测试 API 接口的正确性，包括请求解析、响应生成和错误处理。

### 7.3 E2E 测试规范

关键用户流程应进行端到端测试，验证完整的业务流程是否正常。E2E 测试应使用浏览器自动化工具，如 Playwright 或 Cypress。测试用例应覆盖用户的主要操作路径，如登录、知识创建、知识审核等。测试数据应与生产数据隔离，避免测试污染真实数据。E2E 测试应在 CI/CD 流程中自动运行，确保代码变更不会破坏关键功能。

## 8. 性能规范

### 8.1 前端性能规范

页面首次加载时间应控制在 3 秒以内，关键内容应在 1.5 秒内呈现。图片应进行压缩和懒加载，非视口内的图片应延迟加载。使用代码分割和懒加载减少初始包体积，提升首屏加载速度。列表应使用虚拟滚动技术，支持大量数据的流畅滚动。避免不必要的重渲染，使用 React.memo、useMemo、useCallback 优化组件性能。减少不必要的状态更新，避免全局状态频繁变更导致的级联更新。

### 8.2 后端性能规范

API 响应时间应控制在 200ms 以内，复杂查询不超过 1 秒。应使用数据库索引优化查询性能，避免全表扫描。对于耗时操作应使用异步处理，避免阻塞主线程。缓存应合理使用，减少重复计算和数据库访问。应控制返回数据量，使用分页和字段选择避免过度返回。应进行性能测试和压力测试，确保系统在高并发下的稳定性。

## 9. 安全规范

### 9.1 前端安全规范

用户输入应进行校验和过滤，防止 XSS 攻击。敏感操作应验证用户身份和权限，防止 CSRF 攻击。应使用 HTTPS 加密传输，避免中间人攻击。敏感数据如 Token 应存储在内存或 HttpOnly Cookie 中，避免 XSS 窃取。应避免在前端代码中硬编码密钥和密码。应使用 CSP（Content Security Policy）减少 XSS 攻击面。

### 9.2 后端安全规范

用户输入应进行严格的校验和过滤，使用参数化查询防止 SQL 注入。应使用成熟的认证方案，如 JWT、OAuth2，不自己实现认证机制。应使用 BCrypt 等专业哈希算法处理密码，不使用 MD5 或 SHA1。应限制接口的访问频率，防止暴力破解和 DDoS 攻击。应记录安全相关的日志，便于审计和追踪。敏感数据应加密存储和传输，密钥应独立管理和轮换。
