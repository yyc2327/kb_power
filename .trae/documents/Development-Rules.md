# 企业级知识库管理系统 - 开发规则

## 1. Git 工作流规范

### 1.1 分支策略概述

本项目采用 GitFlow 工作流作为主要的分支管理策略，该策略通过明确划分不同类型分支的职责，确保开发过程有序进行，同时保持代码库的稳定性和可追溯性。GitFlow 策略包含长期分支和临时分支两大类，长期分支包括主分支（main）和开发分支（develop），它们始终存在于代码库中，分别代表生产环境代码和开发集成代码。临时分支包括功能分支（feature）、发布分支（release）、热修复分支（hotfix）和缺陷修复分支（bugfix），它们在完成使命后会被合并或删除。

### 1.2 分支命名规范

所有分支必须遵循统一的命名规范，以便于识别分支类型和用途。功能分支的命名格式为 feature/功能描述-任务编号，例如 feature/knowledge-graph-123 表示与知识图谱相关的 123 号任务。发布分支的命名格式为 release/版本号，例如 release/v1.0.0 表示 1.0.0 版本的发布准备分支。热修复分支的命名格式为 hotfix/问题描述-紧急程度，例如 hotfix/login-crash-critical 表示登录崩溃的紧急修复。缺陷修复分支的命名格式为 bugfix/问题描述-任务编号，例如 bugfix/search-timeout-456 表示搜索超时问题的修复。分支名称中的功能描述和问题描述应使用英文单词或拼音缩写，单词之间使用连字符分隔，避免使用中文或特殊字符。

### 1.3 主分支管理

main 分支是代码库的主干，代表生产环境的最新稳定版本。该分支的代码始终保持可部署状态，任何未经测试验证的代码都不应直接提交到 main 分支。main 分支受到分支保护规则的保护，禁止直接推送（force push）和强制合并（force merge），所有变更必须通过 Pull Request 并经过代码审查后才能合并。main 分支的提交历史被视为发布的版本记录，每个合并到 main 的提交都应附带清晰的版本标签（tag），标签命名遵循语义化版本规范（SemVer）。

develop 分支是开发集成的核心分支，汇集了所有已完成的功能开发和缺陷修复。该分支作为功能测试和集成测试的基础，所有新功能的代码最终都应合并到 develop 分支。develop 分支同样受到保护，但相对于 main 分支允许更灵活的代码审查流程。在功能开发阶段，develop 分支的代码可能存在不稳定情况，这是正常的开发迭代过程。develop 分支应保持每日至少一次与 main 分支的同步，避免长期分离导致合并冲突累积。

### 1.4 功能分支流程

功能分支用于开发新的功能模块或进行重大的代码重构，每个功能分支应专注于单一的功能目标。创建功能分支时，应从最新的 develop 分支派生，并在分支名称中清晰标识功能和任务编号。开发人员在功能分支上进行开发工作，期间可以频繁提交代码，建议每天至少提交一次以避免代码丢失。功能开发完成后，需要将 develop 分支的最新代码合并到功能分支，解决可能的冲突，然后创建 Pull Request 请求合并到 develop。Pull Request 的描述应包含功能说明、测试情况、影响范围和迁移指南等信息，方便审查者了解变更内容。功能分支合并到 develop 后，该分支应立即删除，保持代码库的整洁。

### 1.5 发布分支流程

当 develop 分支达到可发布状态时，应从 develop 分支创建发布分支，发布分支的命名格式为 release/版本号。发布分支的主要目的是进行发布前的最终调整和缺陷修复，不应再引入新的功能。发布分支可以进行小范围的缺陷修复和文档更新，但应避免大规模的代码变更。如果在发布分支发现重大缺陷，应优先在 develop 分支修复，然后 cherry-pick 到发布分支。发布测试通过后，将发布分支同时合并到 main 和 develop，main 分支的合并应创建版本标签。发布分支合并完成后应立即删除，版本标签应包含版本号和发布日期信息。

### 1.6 热修复分支流程

热修复分支用于处理生产环境的紧急问题，当线上出现影响业务的严重缺陷时，应立即从 main 分支创建热修复分支。热修复分支的命名应简洁明了，能够快速传达问题性质和紧急程度。热修复开发完成后，应同时合并到 main 和 develop 分支，确保修复不会在后续开发中丢失。如果存在对应的发布分支，热修复也应合并到发布分支。热修复合并完成后应立即删除，并创建相应的版本标签说明修复内容。热修复的代码审查流程可以适当简化，但仍需至少一名团队成员的确认。

## 2. 提交规范

### 2.1 提交信息格式

每次代码提交都应包含有意义且规范的提交信息，清晰的提交信息有助于追踪变更历史和理解代码演进过程。提交信息由标题行和正文组成，标题行是必填项，应简明扼要地描述本次提交的内容，标题行长度不应超过 72 个字符。标题行应使用祈使语气和现在时态，例如 "Add search functionality" 而不是 "Added search functionality" 或 "Adds search functionality"。正文部分是可选的，用于详细说明变更原因、变更内容和注意事项，正文与标题之间应留有空行，正文中的多行内容应使用换行符分隔。

### 2.2 提交类型标识

提交标题应以类型前缀开头，标识本次提交的类型，类型前缀应使用方括号包裹。类型标识及其含义定义如下：feat 表示新增功能，是用户可见的功能改进；fix 表示缺陷修复，是针对已知问题的错误修正；docs 表示文档更新，包括代码注释、README、API 文档等；style 表示格式调整，不影响代码逻辑的样式变更，如空格、缩进、换行等；refactor 表示代码重构，在不改变外部行为的前提下优化代码结构；perf 表示性能优化，提升代码执行效率的改进；test 表示测试相关，包括新增测试用例或修复现有测试；chore 表示构建过程或辅助工具的变更，如依赖更新、构建脚本修改等。

### 2.3 提交作用域

提交标题可以在类型后添加作用域标识，作用域使用括号包裹，用于标识本次提交涉及的项目模块。常见的作用域包括 core 表示核心架构变更、ui 表示用户界面相关、api 表示接口相关、db 表示数据库相关、auth 表示认证授权相关、graph 表示图谱相关等。例如 "feat(ui): add knowledge card component" 表示在 UI 模块新增知识卡片组件，"fix(api): resolve search timeout issue" 表示修复 API 模块的搜索超时问题。如果提交涉及多个作用域，可以使用逗号分隔或省略作用域标识。

### 2.4 提交内容原则

每次提交应遵循原子性原则，即每次提交只包含一个逻辑变更，避免将多个不相关的变更混合在一次提交中。原子性提交有助于问题的定位和回滚，当某个变更引发问题时，可以精确地回退到问题引入之前的提交。如果需要进行多项不相关的修改，应拆分为多次独立的提交，每次提交都有清晰的变更描述。提交内容应包含足够的测试用例，新功能的提交应附带相应的单元测试，缺陷修复的提交应包含能够复现问题的测试用例。提交前应确保代码能够正常编译和运行，破坏构建的提交是不被允许的。

### 2.5 提交频率建议

鼓励开发人员进行频繁的小规模提交，频繁提交有助于保存工作进度和追踪问题，但每次提交都应是有意义的变更。建议在完成一个小的功能点、修复一个缺陷或进行一次重构后进行提交，避免“等我做完再提交”的工作方式。对于正在进行中的工作，可以使用 Git 的 stash 功能临时保存，避免提交不完整的代码。如果一天的工作结束时仍有未完成的变更，应将已完成的变更分离出来单独提交，未完成的变更可以暂存在工作区或单独的分支。

## 3. Pull Request 规范

### 3.1 Pull Request 创建流程

Pull Request 是代码合并到主分支的主要方式，应在完成开发和本地测试后创建。创建 Pull Request 前，应确保目标分支（通常是 develop）的最新变更已合并到当前分支，所有冲突已解决。Pull Request 的标题应简洁明了，能够概括本次变更的核心内容，标题格式应与提交信息类似，包含类型前缀和简短描述。Pull Request 的描述应包含详细的变更说明，包括新增功能的介绍、解决的问题、影响范围、测试说明、截图或演示视频（如果是 UI 变更）、迁移说明（如果有）等。描述模板可以使用项目预设的模板，确保包含所有必要的信息。创建 Pull Request 后，应指定至少一名代码审查者，并通知相关团队成员进行评审。

### 3.2 代码审查要求

代码审查是保障代码质量的重要环节，所有 Pull Request 都必须经过至少一名团队成员的审查才能合并。审查者应关注代码的功能正确性、逻辑合理性、设计模式选择、性能影响、安全隐患和可维护性等方面。审查者应仔细阅读变更代码，对于不清晰或有疑问的地方应在评论中提出，提问应具体明确，避免模糊的反馈。审查者应验证测试的充分性，包括单元测试覆盖率、边界条件处理、异常情况处理等。审查者如果发现问题，应明确标注问题的严重程度：blocker 表示必须修复才能合并，minor 表示建议修复但非强制，question 表示需要进一步澄清。审查通过的 Pull Request 应获得 Approve 状态，未通过的应获得 Request Changes 状态。

### 3.3 合并前检查清单

Pull Request 合并前必须满足以下条件：所有审查者都已 Approve，不存在 Request Changes 状态的未解决反馈；所有持续集成检查（CI）都已通过，包括代码构建、单元测试、代码质量检查、安全扫描等；代码冲突已解决，与目标分支保持同步；分支已更新到最新版本，不存在落后于目标分支的情况。对于涉及数据库变更的 Pull Request，应确认已提供数据库迁移脚本；对于涉及配置变更的 Pull Request，应确认配置项已正确添加；对于涉及接口变更的 Pull Request，应确认接口文档已同步更新。合并前应再次确认变更范围是否符合预期，避免意外合并无关代码。

### 3.4 合并策略选择

本项目采用 Squash and Merge 作为默认合并策略，将功能分支的所有提交压缩为一个提交合并到目标分支。Squash 合并有助于保持目标分支的历史简洁，避免大量中间提交污染版本历史。提交信息应使用 Pull Request 的标题作为合并后的提交信息标题，正文应包含 Pull Request 链接和审查通过的说明。对于包含多个逻辑独立的变更的 Pull Request，可以考虑使用 Merge Commit 策略，保留完整的提交历史。Rebase and Merge 策略适用于需要保持线性历史的分支，但应谨慎使用，因为会改写提交历史。发布分支和热修复分支应使用 Merge Commit 策略，以便保留完整的发布记录。

### 3.5 审查反馈规范

审查者提供的反馈应具体、建设性和专业，反馈意见应指出具体的问题位置和修改建议，避免空泛的评价。反馈应区分不同的重要性级别，帮助提交者合理安排修复优先级。对于代码风格和格式的问题，应引导开发者参考项目规范文档，而不是逐条指出。对于复杂的设计决策问题，建议进行面对面或视频沟通，深入讨论后再做决定。审查者和提交者都应保持专业和礼貌的沟通态度，对事不对人，尊重彼此的工作成果。审查讨论应在 Pull Request 的评论中进行，确保讨论内容有记录可追溯，避免使用即时通讯工具进行关键的审查讨论。

## 4. 发布管理

### 4.1 版本号规范

本项目采用语义化版本规范（SemVer）进行版本管理，版本号格式为主版本号。次版本号。修订号（MAJOR.MINOR.PATCH）。主版本号在有破坏性变更时递增，包括不兼容的 API 变更、大规模架构调整等；次版本号在新功能向后兼容时递增，包括新增功能模块、重大功能改进等；修订号在向后兼容的问题修复时递增，包括缺陷修复、小幅优化等。预发布版本号在正式发布前使用，格式为版本号-预发布标识，如 v1.0.0-alpha.1、v1.0.0-beta.2 等。版本号递增应由项目负责人或指定人员执行，开发人员不应擅自修改版本号。

### 4.2 发布流程定义

正式发布前应完成以下准备工作：首先确认所有计划内的功能都已实现并通过测试，没有阻塞级别的问题未解决；其次更新版本号和更新日志（CHANGELOG），详细记录本版本的变更内容；然后进行发布前的代码冻结，冻结期间只允许修复严重的缺陷，不允许引入新功能。发布前应执行完整的回归测试，确保新版本不会破坏已有功能。发布应选择业务低峰期进行，并提前通知所有相关方。发布过程应全程记录，包括发布时间、发布人员、变更内容等。发布完成后应立即进行线上验证，确认系统正常运行。

### 4.3 发布后跟踪

发布完成后应密切关注系统运行状态，监控以下指标：系统可用性、响应时间、错误率、资源使用率等。应在发布后 24 小时内安排专人值班，及时响应可能出现的问题。如果发现严重问题，应立即启动回滚流程，将系统恢复到上一稳定版本。发布后应收集用户反馈，记录发现的问题和改进建议，作为下一版本规划的输入。应定期回顾发布过程，总结经验教训，优化发布流程和工具。

### 4.4 回滚机制

当发布出现严重问题且短时间内无法修复时，应启动回滚机制，恢复到上一稳定版本。回滚决策应由技术负责人或项目经理根据问题的严重程度和影响范围决定。回滚前应确认上一版本部署包和数据库迁移脚本的可用性。回滚过程应保持冷静和有序，按照预定的回滚步骤执行，避免人为操作失误。回滚完成后应立即通知所有相关方，说明回滚原因和预计恢复时间。回滚后应深入分析问题根因，完成修复并经过充分测试后再择机重新发布。

## 5. 持续集成与部署

### 5.1 CI/CD 流程设计

本项目采用全自动的持续集成和持续部署流程，每次代码提交和 Pull Request 都会触发自动化流水线。CI/CD 平台选择 GitHub Actions 或 GitLab CI，根据团队现有的技术栈决定。流水线包括以下阶段：代码检出、依赖安装、代码构建、静态分析、单元测试、集成测试、安全扫描、构建产物构建和发布。流水线中的每个阶段都应配置超时时间，避免无限等待。流水线失败时，应自动通知相关开发人员，并阻止代码合并到受保护分支。

### 5.2 环境管理

本项目维护三套环境：开发环境（dev）、预发布环境（staging）和生产环境（production）。开发环境用于日常开发调试，代码合并到 develop 分支后自动部署，对应部署地址为 dev.example.com。预发布环境用于发布前的最终验证，代码合并到 release 分支后自动部署，对应部署地址为 staging.example.com。生产环境用于正式提供服务，代码合并到 main 分支并打标签后手动触发部署，对应部署地址为 www.example.com。各环境的配置应使用环境变量管理，避免硬编码敏感信息。

### 5.3 质量门禁

持续集成流水线中应设置质量门禁，只有通过所有质量检查的代码才能进入下一阶段。代码覆盖率门禁要求新增代码的测试覆盖率不低于 80%，低于此阈值时构建失败。代码质量门禁使用 ESLint 和 TypeScript 编译器进行检查，存在错误或严重警告时构建失败。安全扫描门禁使用 OWASP 依赖检查和代码安全扫描工具，发现高危漏洞时构建失败。性能基准门禁在集成测试中收集性能指标，性能明显下降时构建失败。质量门禁的阈值可以根据项目实际情况调整，但调整前需要经过团队讨论和确认。

## 6. 代码所有权与协作

### 6.1 模块所有权

为了明确责任和提高效率，项目中的核心模块应指定明确的所有者。模块所有者对该模块的代码质量和架构演进负有主要责任，负责审查涉及该模块的所有 Pull Request。模块所有者应保持对模块最新进展的了解，当有涉及模块的重大决策时，应参与讨论并给出专业意见。一个模块可以有一个或多个所有者，当所有者暂时无法履行职责时，应指定代理人。如果模块所有者发生变更，应进行正式的知识交接，确保模块的持续健康发展。

### 6.2 协作冲突处理

当多个开发人员对同一模块进行修改时，可能产生代码冲突和技术决策分歧。对于代码冲突，应鼓励开发人员通过沟通协商解决，而不是简单粗暴地强制合并。对于技术决策分歧，应基于技术合理性和项目利益进行讨论，必要时可扩大讨论范围征求更多意见。如果争议无法在团队内部解决，应升级到技术负责人或架构师进行裁决。裁决结果应被所有相关方接受和执行，即使个人有保留意见也应遵循团队决定。争议解决后应总结经验教训，完善相关规范避免类似问题再次发生。

### 6.3 知识共享

鼓励团队成员进行技术分享和知识传播，提升团队整体的技术能力和协作效率。应定期组织技术分享会，每位开发人员都应有机会分享自己的技术心得或项目经验。重要的技术决策应形成文档，记录决策背景、考虑因素和最终结论，便于新成员了解和后续追溯。对于复杂的问题解决过程，应鼓励撰写技术博客或内部文档，分享问题分析和解决方法。代码审查不仅是质量保障手段，也是知识传播的重要途径，审查过程中的讨论对参与双方都有价值。
